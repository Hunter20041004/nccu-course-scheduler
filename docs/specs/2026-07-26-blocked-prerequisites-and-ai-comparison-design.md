# 擋修條件遺漏 ＋ AI 課綱比較失效 — 設計文件

> 2026-07-26｜Claude 診斷。實作交給 Codex，工單見根目錄 `HANDOFF.md`。

使用者回報兩個 bug。以下是實際查證後的根因與修法設計。
**Bug A 已用真實政大資料完整證實；Bug B 的主因有強力佐證但尚未對真實 Gemini API 驗證**——
差別很重要，Codex 實作時請照工單裡的驗證步驟補上。

---

## 名詞先講白話

- **擋修**：政大選課系統的硬性阻擋。課程備註寫「擋修中會(二)」，代表**沒修過中會（二）的人，選課系統直接不讓你加選**，不是「建議先修」而已。
- **eligibility rule（資格規則）**：本專案用來描述「這門課有什麼門檻」的資料結構。每條規則有一個 `conditionId`，使用者在「條件」區勾選代表「我符合這項」。
- **thinking model（思考型模型）**：像 `gemini-3.5-flash` 這類會先在心裡推理一輪、再輸出答案的模型。關鍵在於**推理過程的 token 跟最終輸出共用同一個長度預算**——想太久，答案就會被砍斷。

## Bug A：擋修沒有變成可勾選的條件

### 症狀

使用者加入「高級會計學（一）」（課號 `303033011`），畫面下方「選課條件與官方備註」
如實列出「擋修中會(二)。」，但**修課資格顯示「條件符合」**，而且條件區沒有出現
「我修過中會（二）」可以勾。等於系統看得到這句話，卻沒把它當一回事。

### 查證

直接打政大公開課程 API 取得原始資料：

```
https://es.nccu.edu.tw/course/zh-TW/:sem=1151 303033011 /
```

回傳的 `note` 欄位是 `＠備註:擋修中會(二)。`，經 `normalizeRestriction()` 去掉
`＠備註:` 前綴後，`restrictionText` = `擋修中會(二)。`。資料本身完全正常。

### 根因

`src/nccu-course-notes.mjs` 的 `classifyOfficialNotes()` 是一條 if-else 分類鏈，
負責把官方備註拆成「資格規則／時間備註／授課形式／考試事件／學程標籤／純資訊」。
它目前認得的資格句型只有三種：

| 既有規則 | 比對條件 |
|---|---|
| 僅限某某學生修讀 | `/^僅限(.+?)學生修讀$/` |
| 限開頭的限制 | `/^限(?!制)[^。]+/` |
| 須／需 … 先修／修習／具備 | `/(?:須\|需).*(?:先修\|修習\|具備)/` |

**「擋修」三種都不符合**，於是掉進最後的 `informationNotes`（純資訊），
不會產生任何 `eligibilityRules`。而 `evaluateEligibility()` 在沒有規則時就回
`eligible` → 畫面顯示「條件符合」。

一句話：**分類器沒學過「擋修」這個詞**。

### 影響範圍

抓「會計」與「擋修」兩組真實搜尋結果（99 門課）掃過，
**13 門不重複的課**踩到這個坑，包含中級會計學（一）各班、成本管理會計（一）各班、
審計學（一）（二）、初級會計學（二）、高級會計學（一）。
會計系的必修鏈幾乎整條都受影響——對會計系學生來說這不是小 bug。

### 真實資料的所有變化型（實作必須全部處理）

以下每一條都是真的存在於 115-1 的備註原文：

**要抓出來的：**

| 原文 | 應產生的條件 |
|---|---|
| `擋修中會(二)。` | 我修過中會(二) |
| `擋修初會（二）,英語授課，ETP優先。` | 我修過初會(二) |
| `會二乙，擋修初會（二）。第一堂課請務必出席…` | 我修過初會(二) |
| `擋修審計學（一），以系統遞補名單為主…` | 我修過審計學(一) |
| `不論學生身份，修習本課程皆須繳學分費，擋修初會(二)。` | 我修過初會(二) |
| `會二甲，擋修初會(一)、初會(二)，擋修者請勿選修，不簽同意修課單。` | **兩條**：我修過初會(一)、我修過初會(二) |
| `財政三、財管二，擋修初會(一)、初會(二)。` | **兩條** |

**絕對不能誤抓的（「擋修」在講流程，不是課名）：**

| 原文片段 | 為什麼不能抓 |
|---|---|
| `擋修者請勿選修` | 「者」不是課名 |
| `如被擋修，請於加退選結束前…` | 「擋修」後面直接接逗號 |
| `設定允許擋修後，方得於系統上選課` | 「後」不是課名 |
| `同時修讀者請完成擋修程序` | 「程序」不是課名 |

### 建議修法

在 `classifyOfficialNotes()` 的分類鏈**最前面**加一段擋修抽取。設計要點：

1. **抽取規則**：找出所有 `擋修` 後面接的內容，一路吃到下一個
   `，` `,` `。` `；` `;` 或換行為止；再用 `、` 切開成多門課。
   （`、` 是「同一句列多門課」的分隔符，`，`／`,` 才是「換一件事講」。）
2. **排除清單**：抽出來的字串若以 `者｜程序｜單｜後｜前｜時｜流程｜規則｜規定｜資格｜條件｜名單｜作業`
   開頭，就丟掉——這些是在講流程不是課名。空字串也丟掉。
3. **正規化課名**：全形括號 `（）` 轉半形 `()`、去掉空白，
   讓 `初會（二）` 與 `初會(二)` 收斂成同一個 key。
4. **`conditionId` 用課名、不要用課號**：
   `prerequisite-course:初會(二)`，**不要**用既有的 `official-restriction:<課號>` 格式。
   - 理由一：同一門課可能擋修兩門（初會一＋初會二），用課號當 id 會**互相蓋掉**，
     `buildConditionDefinitions()` 依 `conditionId` 去重，只會留下第一條。
   - 理由二：用課名當 id，**條件可以跨課共用**——診斷時實測 13 門課只會收斂成
     4 個勾選項（我修過初會(一)／初會(二)／中會(二)／審計學(一)）。
     學生勾一次「我修過初會(二)」，所有相關課程同時解鎖，這是明顯更好的體驗。
5. **`enforcement` 用 `required`**：擋修是系統硬擋，不是「可以找老師談」。
6. **不要 `return`、要繼續往下跑分類鏈**：擋修常和其他備註寫在同一句
   （`擋修初會（二）,英語授課，ETP優先`），提早 return 會弄丟後面的授課形式資訊。
   這段是**純新增**，不改動任何既有分類行為。

建議欄位長相：

```
conditionId:          prerequisite-course:中會(二)
conditionLabel:       我修過中會(二)
conditionDescription: 政大官方擋修：沒修過中會(二)的話，選課系統會擋下這門課。
enforcement:          required
rationale:            官方擋修：須先修過中會(二)
source:               nccu-official
confidence:           high
```

### 修好之後的預期行為（診斷時已實測）

以 `303033011` 高級會計學（一）為例：

| 使用者狀態 | `evaluateEligibility()` 結果 |
|---|---|
| 還沒回答 | `review` — 理由「官方擋修：須先修過中會(二)」（不再是錯誤的「條件符合」） |
| 勾了「我修過中會(二)」 | `eligible` |
| 明確回答沒修過 | `blocked` — 加不進課表 |

條件區會出現一個「我修過中會(二)」的勾選項，摘要顯示「影響 N 門候選課」。

### ⚠️ 一個要注意的副作用

這個修法會讓 13 門會計課從「條件符合」變成「資格待確認」。
這是**正確的**（原本是假的綠燈），但畫面上會多出黃色待確認狀態。
Codex 實作後請跑截圖自檢，確認待確認狀態的視覺不會讓人以為壞掉了。

## Bug B：AI 課綱比較回「AI 課程比較格式不正確」

### 症狀

勾選 2 門課、按「AI 比較」，畫面回「AI 課程比較格式不正確。」

### 錯誤來自哪裡

這句話只有一個來源：`src/course-comparison.mjs` 的 `parseCourseComparison()`
（第 90 行 JSON 解析失敗，或第 134 行欄位驗證不通過）。

**可以先排除的**：
- 不是 API Key 或額度問題 → 那會回「這組 API Key 無法使用」或「今天的免費額度已用完」
- 不是模型叫不到 → 那會回「Gemini 暫時無法回應」
- 不是課綱讀不到 → 那會回「至少需要兩門可讀取的官方課綱才能比較」
- 不是回覆完全空白 → 那會回「Gemini 回覆格式不正確」（另一句話）

**結論：Gemini 有回東西，但那串文字沒辦法組成合法的比較 JSON。**

### 主因（強力佐證，但尚未對真實 API 驗證）

`src/ai-service.mjs` 第 81 行：

```js
maxCompletionTokens: 2_600,
```

`GEMINI_RECOMMENDATION_MODEL` 是 `gemini-3.5-flash`，**思考型模型**。
它的推理 token 和輸出 token **共用** `maxOutputTokens` 這一個預算。
預算用完時 Gemini 會直接切斷輸出（`finishReason: MAX_TOKENS`），
回傳半截 JSON → `JSON.parse()` 炸掉 → 使用者看到「格式不正確」。

**佐證一：輸出本身就快塞滿預算。** 用真實中文長度估算 prompt 要求的 JSON：

| 比較門數 | JSON 長度 | 約需 output token |
|---|---|---|
| 2 門 | 792 字元 | 約 800 |
| 3 門 | 993 字元 | 約 1,000 |
| 5 門（上限） | 1,395 字元 | 約 1,400 |

2,600 的預算，五門課時只剩約 1,200 token 給推理——而輸入是兩份以上、
每份最長 24,000 字的課綱，推理量遠遠不止這些。

**佐證二（最關鍵）：同一支檔案裡的排課推薦功能有做防護，比較沒有。**
`recommendCoursePlans()` 的 system prompt 明文寫著
「文字務必精簡：summary 60 字內；每個 title 20 字內、reason 80 字內…」，
就是為了塞進它的 2,200 預算。
`compareCourseSyllabi()` 的 prompt **一條字數限制都沒有**，卻只多給 400 token。
會寫出前者字數限制的人，顯然踩過截斷；後者是漏掉了同樣的處理。

### 幫兇一：重試機制被關掉了

`requestWithSchemaRetries()` 本身寫得很好——第一次回覆驗證失敗時，
會把錯誤訊息附回去要求模型重寫。預設 `maxAttempts = 2`。

但 `compareCourseSyllabi()` 呼叫時**傳了 `1`**（`src/ai-service.mjs` 第 92 行），
`1` 代表「只試一次」，整套自我修復邏輯**完全不會執行**。
所以只要模型抖一次，使用者就直接吃到錯誤，連一次補救都沒有。

### 幫兇二：餵給 AI 的課綱有兩成是空白

`src/nccu-syllabus.mjs` 的 `extractSyllabusText()` 清理空白時，
`replace(/[ \t\f\v]+/g, ' ')` **漏掉了 `\r`**。政大課綱頁是 CRLF 換行，
所以 `\n{2,}` 那道收合完全失效——`\r\n\r\n\r\n…` 原封不動留著。

實測兩份真實課綱：

| 課程 | 目前長度 | 清乾淨後 | 浪費 |
|---|---|---|---|
| 070394021 人工智慧方法與工具 | 5,886 字元 | 4,401 | 25% |
| 783004001 人工智慧程式設計 | 7,466 字元 | 5,998 | 20% |

兩成的輸入是純空白，除了浪費預算，還會吃掉 24,000 字上限的額度
（長課綱會因此被截掉真正有用的內容）。

### 建議修法（三段，可獨立驗證）

1. **把預算調大到 8,000**，並在比較的 system prompt 補上字數限制
   （比照推薦功能的寫法：summary 100 字內、每門課各欄位 50 字內、
   sharedTopics 最多 5 項、limitations 最多 3 項…）。
   一個放寬預算、一個壓住輸出長度，兩邊一起做才穩。
2. **把 `maxAttempts` 從 `1` 改成 `2`**，讓自我修復真的會跑。
   （代價：最壞情況多打一次 API。使用者用自己的免費額度，可接受。）
3. **`extractSyllabusText()` 加一行把 `\r\n?` 正規化成 `\n`**，
   放在現有空白收合之前。

### 另外建議：讓錯誤訊息說人話

`src/gemini-client.mjs` 目前把 `finishReason` 整個丟掉。
建議偵測 `finishReason === 'MAX_TOKENS'` 時直接丟一個明確錯誤
（例如 `AI_RESPONSE_TRUNCATED` / 「AI 回覆長度超出上限而被截斷，請稍後重試。」）。

**這件事的價值不只是文案**：如果我對主因的判斷是對的，這行程式會讓問題當場現形；
如果判斷錯了，使用者至少也不會再看到一句查不出原因的「格式不正確」。
狀態碼用 502，worker 既有的 `retryable` 邏輯會自動把它標成可重試。

### ⚠️ 誠實交代：這部分還沒對真實 API 驗證

上面的推論是從程式碼、真實課綱長度、以及推薦／比較兩段程式的落差推出來的，
邏輯鏈完整，但**我沒有 Gemini API Key，無法對真的 Gemini 打一次來證實**。
現有測試全部是 mock，mock 永遠乖乖回合法 JSON，所以這個 bug
在單元測試裡**永遠不會出現**——這正是全域規則說的「mock 邊界」陷阱。

因此工單裡有一條**必要的驗證步驟**：用真實 Key 跑一次真的比較。
如果驗證後發現不是截斷，`AI_RESPONSE_TRUNCATED` 那段程式會直接告訴我們真正的
`finishReason`，再回頭修正判斷。
